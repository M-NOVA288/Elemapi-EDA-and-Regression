# 02 – SLO & Log Analyzer (Python)

A command-line tool that reads structured JSON logs and answers the questions an on-call engineer
asks during and after an incident:

- **Are we meeting our SLO, and how much error budget is left?**
- **Would our alerts have paged, and when?** Multiwindow, multi-burn-rate rules from the Google SRE Workbook, replayed minute by minute.
- **When did things go wrong?** Rolling z-score anomaly detection on per-minute error counts.
- **Which endpoint is slow?** p50/p95/p99 latency and error rate per event.

Standard library only (no installs). Built to read the logs emitted by my
[Deal Liaison](https://github.com/M-NOVA288/Deal-liaison-w-Vercel-Supabase) service, which writes one JSON
object per line: `{"ts", "level", "event", "ms", "ok", "requestId"}`.

## Run it

```bash
cd 02-slo-log-analyzer
python -m slo_toolkit report data/sample_logs.jsonl --slo 0.995
python -m slo_toolkit report data/sample_logs.jsonl --event webhook.stripe   # one event family
python -m slo_toolkit generate my_logs.jsonl --minutes 240                   # new synthetic data
python -m unittest -v                                                        # 13 tests
```

## Example output

`data/sample_logs.jsonl` is **synthetic**: 4 hours of traffic generated by `slo_toolkit/generate.py`
with a 15-minute incident injected at 16:30 UTC (35% errors, 6x latency, like an exhausted database
connection pool). It is not production data.

```
  health.check                       1,174  2.13%    122    450    968
  http.analyze                       3,175  2.46%     62    258    506
  http.checkout                        898  2.00%    470   2171   3875
  webhook.stripe.failed                 13 100.00%   2016   4006   4006
  webhook.stripe.processed             607  0.00%    298    659   2026
```

**Reading it:**
- The anomaly detector flags the incident from its **first minute** (16:30) through its last (16:44).
- The fast-burn page fires at **16:43**, 13 minutes in. That's the design trade-off of burn-rate alerts: they need enough of the 1-hour window to be bad before paging, which prevents pages for brief blips. A higher error rate trips it sooner.
- Both alerts **resolve on their own** within minutes of recovery, because the short window (5 or 30 min) must also be burning. That's what stops alerts that keep firing for an hour after a fix.
- Checkout p99 (3.9 s) and webhook failures point to where the incident hurt users most.

## How it works

| Module | What it does |
|---|---|
| [`parse.py`](slo_toolkit/parse.py) | Reads JSON lines; malformed lines are counted and skipped, never crash the run |
| [`stats.py`](slo_toolkit/stats.py) | Nearest-rank percentiles; latency and error rate per event |
| [`slo.py`](slo_toolkit/slo.py) | SLI, error budget, burn rate; replays alert rules (1h/5m at 14.4x → page, 6h/30m at 6x → ticket) |
| [`anomaly.py`](slo_toolkit/anomaly.py) | Per-minute series (including empty minutes); rolling z-score whose baseline **excludes already-flagged points**, so a long incident doesn't become the new normal; groups minutes into incident windows |
| [`generate.py`](slo_toolkit/generate.py) | Seeded synthetic traffic with an injected incident, for demos and tests |

## Tests

13 `unittest` tests, run in GitHub Actions: budget math, burn rate, no alerts on healthy traffic,
the injected incident pages and then resolves, the detector covers the whole incident, a flat baseline
doesn't flag a single blip, malformed lines are tolerated.

## Limits

- Batch analysis of a file, not a streaming service. In production these rules would run in a metrics system (Prometheus recording + alerting rules, or CloudWatch/Grafana alerts) on live data.
- Burn-rate replay is O(minutes × records); fine for hours of logs, not for months. A real implementation would pre-aggregate per minute.
